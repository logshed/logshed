# Specification: Frontend Specification (React + Vite + Tailwind)

Parent document: [docs/SPEC.md](../../docs/SPEC.md)

## 1. Overview & Architecture
The LogShed frontend is a responsive single-page web application built with React, Vite, and Tailwind CSS. The interface is tailored for dense, real-time log observation, incident investigation, rule configuration, and system administration. Production builds are bundled directly into `backend/app/static/` and served by FastAPI with HTML5 History API fallback routing to `index.html`.

Times are shown in the server time zone (`server_timezone` from `GET /api/settings`), the same zone the log stream and search presets use, falling back to browser time until settings load. This covers the log stream, alert history and incident details, "Last triggered" on alert rules, maintenance end and next-run times (also in the navbar banner), the prune cut-off, the digest's last run, the model cache time and API token dates. Date and time inputs use the same zone and show its name beside them: the Console custom From and To pickers (switching from "Today" to "Custom" fills From with midnight on the server clock) and the maintenance "Specific End Time" picker (`toLocalDatetimeInputString`, `fromLocalDatetimeInputString` and `startOfTodayIso` in `utils/formatters.ts`). A time the server clock shows twice (clocks going back) is read as its first occurrence, and a time it skips (clocks going forward) is moved forward by the length of the gap, as maintenance schedules are. While the zone is unknown (settings not loaded, or `server_timezone` is `null`) the inputs take browser time and say "browser time".

## 2. Navigation Hierarchy
The frontend implements single-page HTML5 History API routing across four top-level navigation destinations:
- **`/` (Logs / Console):** Live streaming log console with virtual scrolling, search, filters, saved views, and context inspection.
- **`/rules` (Rules & Alerts Hub):** Unified hub managing alert rules, ingestion drop rules, incident history, maintenance windows, and built-in canary presets.
- **`/storage` (Storage Metrics):** Storage metrics dashboard displaying database file sizes, host mount disk usage, 30-day volume trends, manual prune triggers, and database vacuum utilities. Lowering retention or purging expired data first shows a preview modal listing the logs, history items, metrics and AI audit records that would be deleted.
- **`/settings` (Settings & Aliases):** Application settings, AI provider configuration, notification channels, API & MCP access, advanced runtime options, and IP-to-Host alias management located at `/settings/aliases`. Top-level requests to `/aliases` automatically redirect to `/settings/aliases`.

Unsaved changes detection and browser exit guards prevent accidental loss of form inputs across settings tabs and modal dialogs. When the prompt holds back a link that leaves Settings (for example "View logs" on a host alias, which opens `/?source=<alias>`), Discard & Leave and Save & Continue open that exact URL, so its filters are kept.

## 3. Core Components & Views

### 3.1 Console Viewer (Live Stream - `/`)
* **Virtual List Implementation (`@tanstack/react-virtual`):**
  * Virtual list container capable of rendering 50,000+ log lines without DOM performance degradation.
  * Dynamic item measurement with parent scroll container integration.
* **Live Streaming & Flow Control:**
  * Real-time Server-Sent Events (SSE) stream consuming incoming log records.
  * Configurable auto-scroll operation with automatic pause detection when the operator scrolls upward. On phones the button reads "Scroll" (or "Paused") and the clear buffer button is left out, so the quick filters keep their room.
  * While paused, new rows join the top of the list and the scroll position moves down by their height, so the rows in view stay put. While the operator is scrolling (a finger on the list, or a scroll event in the last 150 ms, which covers the glide after a flick), new rows are held and counted in the "N new logs at top" banner instead, because phone browsers show a scroll position change during a drag or glide as a jump. Once scrolling stops they join in one batch with one correction. Rows held because the scrollback buffer is full wait for auto-scroll to resume.
  * The Paused button and the "N new logs at top" banner turn auto-scroll back on and scroll smoothly to the top. The scroll events on the way up do not pause it again, so new rows keep it going to the top; touching, wheeling, clicking or a cursor key hands the list back to the operator (or 1.5 s pass).
* **Phone Rows:** Below the `md` breakpoint (767 px and narrower) each row is a three-line card: severity, app and host; the message in two lines; the time and, with AI on, the AI action. Cards are 84 px tall including a 1 px `dark-700` divider (the colour of the toolbar dividers above the list), so where one card ends shows on the dark page. Desktop rows keep their fainter `dark-900` line.
* **Severity Tinting & Badges:**
  * Visual badges reflecting RFC 5424 severity priorities: Emergency / Alert / Critical / Error (Red), Warning (Yellow), Notice / Informational / Debug (Slate / Blue).
* **Navbar Health Figures:** Ingest rate, and on small screens and up queue depth. **Lost: N** (logs LogShed could not queue because its ingestion queue was full; separate from drop rules) appears only when above 0, on every screen size. **UDP lost: N** appears after it only when `udp_receive_errors` is above 0: the syslog UDP messages the kernel discarded because the receive buffer was full. It is separate from Lost, hidden when 0 or unknown, and counts per network namespace (with `network_mode: host` every UDP socket on the host). TCP syslog avoids this loss. The rate's tooltip adds the event loop lag over the last 60 seconds (now, 95th percentile, maximum) when the server reports it. The amber dot before the rate shows "Health check degraded or unreachable" when the health check fails; otherwise it shows "LogShed is near its processing limit" once, on every health poll (every 10 seconds) for 30 seconds, `loop_lag_p95_ms` has been at 50 ms or more, or the ingestion queue has held at least 5,000 logs (half of its 10,000) or Lost has grown since the previous poll. The tooltip names the cause (event loop, queue, or both), and the dot clears at the first poll where neither holds. The health and maintenance polls (one each, in the Navbar; the Rules page follows the Navbar's maintenance result) pause while the browser tab is hidden and run at once when it is shown again, as does the 10 second refresh of Incident History. The 5,000 is `QUEUE_WARNING_DEPTH` in `Navbar.tsx`; a backend test keeps it at half of the server's queue size.
* **AI Controls:** AI actions follow the AI setting (`ai_enabled`, or a stored API key when that field is missing; treated as off until settings load). When AI is off, rows and mobile cards have no "Explain with AI" icon (the desktop table drops its Actions column), the selection bar has no "Run Analysis (N)", and the log detail drawer keeps one muted "Explain with AI" entry (tooltip "AI features are turned off in Settings") that opens the AI modal, which explains how to turn AI on.
* **Empty States:** With filters set and no results: "No logs match the current filters." and a "Clear filters" button. With no filters and an empty buffer while the database has logs (for example after Clear buffer): "Waiting for new logs...". With no logs in the database at all (an unfiltered history page with a total of 0, or a facets response with no apps; the facets' hosts do not count, since configured syslog aliases and Docker hosts, including the Primary Docker host, are listed before they log): a first-run card with the syslog listening port inside the container (`syslog_port` from `GET /api/settings`, UDP and TCP; "1514 by default" until settings load) and a note that devices use the host port mapped to it, a copyable `logger` test command with that port, a "Set up Docker hosts" button that opens Settings > Sources, and a pointer to Sending Logs in the documentation.
* **Quick Filters Bar:** Shown on every screen size. On phones it shares the line under the search box with the Filters button, without the "Quick Filters:" label. Pinned saved views come first, as chips with a bookmark icon; a click applies the view as the Views menu does, the chip of the active view (see Saved Views Menu) is highlighted, and a click on the active view clears its filters again. Selected host and app chips share one highlight style. Then up to 6 host chips and 6 app chips, each group after a small "Hosts" or "Apps" label, ranked by how many rows each has in the loaded buffer (ties alphabetical). Hosts are the top level and apps live under them: host chips come from every host and keep their place while any host or app chip is selected, and hosts with no logs for the selected apps stay in place, dimmed and disabled, with a tooltip saying why. App chips follow the selected hosts: with a host selected they are that host's apps (all selected hosts' apps for several), ranked by their volume there; without one they are all apps. Selecting an app never changes the app chips, and a selected app stays visible when a host is then selected. The host ranking is refreshed when no chip is selected, the app ranking when no app is selected, each when the other filters change and at most every 30 seconds while live, so chips do not move as logs stream in. A selected chip stays visible even when it falls out of the top 6.
* **Pull to Refresh (phones):** Pulling down on the navbar or the search and quick filter area reloads the page. The finger must first move 16px, and the gesture counts as a pull only when it moves at least twice as far down as sideways; a sideways swipe (such as scrolling the quick filter chips) never becomes a pull, even if it drifts down later. Touch events bubble through the React tree, so the filter drawer and the dropdown lists inside these areas reach the handlers too: no gesture becomes a pull while any dialog is open, or when it starts in a dialog, a `role="listbox"` or an element marked `data-no-pull-refresh` (the Host and App and Saved Views popovers).
* **Console URL:** `q`, `severity`, `app`, `source`, `time` (start, a relative preset or an absolute time) and `to` (absolute end time, same format as `time`). A link with `time` and `to` opens the Console on that range in custom-time mode, with the live stream paused. `focus=<log id>` is not a filter: once that log is loaded (paging up to 10 older pages of 500 to find it), the Console pauses auto-scroll, scrolls it to the middle of the list and highlights it in amber; the highlight and the parameter are dropped when the filters change.
* **Selection & Batch Action Bar:**
  * Checkbox multi-select mode (desktop table, 768px and wider) with a floating action bar: `"Run Analysis (N)"` (only when AI is on) and `"Delete (N)"`.
  * Keyboard row cursor (`handleListKeyDown` in `LiveLogStream.tsx`): the log list is one Tab stop (`role="listbox"`, `aria-multiselectable`, named "Log list"; a plain `region` while it has no rows). Up and Down move a cursor from row to row (the first key lands on the first row in view; moving the cursor pauses auto-scroll as scrolling down does, so live rows arriving above it keep the view and the cursor row in place, and a cursor key that scrolls the list to the top, such as Home, leaves it paused), Page Up and Page Down by a screenful less one row, Home and End to the first and last loaded row; the list scrolls to keep the cursor in view, and End near the bottom loads older logs as scrolling does. Enter opens the cursor row in the detail drawer, Space ticks or unticks it, and Shift+Space ticks the range from the last ticked row. Keys with Ctrl, Meta or Alt, and keys pressed on buttons inside the list, are left alone. The list keeps DOM focus and names the cursor row with `aria-activedescendant` (only while that row is rendered); each row is an `option` with `aria-selected`, and the cursor row has a sky outline while the list has focus and the keyboard was used last (a cursor key, Enter or Space shows it, a mouse press on the list hides it), so a mouse user who opens or ticks rows never sees it. Any other row under the mouse turns `dark-800` with a grey (`slate-500`) left edge, grey so it is not taken for a ticked row; a ticked row (sky) or the alert's log (amber) turns a shade brighter under the mouse rather than losing its colour. The cursor follows the log open in the drawer, so closing the drawer leaves it on the last log viewed. Rows' checkboxes and "Explain with AI" icons are mouse and touch targets, not controls (`aria-hidden`, outside the Tab order), because a list option may not contain a control: keyboard and screen reader users open the log (Enter) and use the drawer's "Explain with AI", or tick rows (Space) and use the selection bar's "Run Analysis (N)".
* **Search & Filter Bar (Query Builder & Facet Bars):**
  * Full-text search supporting SQLite FTS5 query syntax, including the `app:`, `host:`, `source:` and `msg:` prefixes that also filter the live stream. New live rows are filtered with the same `AND`, `OR` and `NOT` grouping as history search (`matchesSearchQuery` in `LiveLogStream.tsx`, following FTS5 precedence, tightest first: words side by side, `NOT`, `AND`, `OR`; brackets group). Terms match the way FTS5 does: the text is split into words like the `unicode61` tokenizer (letters and digits form words, accents are ignored), a term of three or more characters matches at the start of a word (`cron` finds `crontab` but not `acronym`), a shorter term only as a whole word unless it ends in `*` (`io` finds `io` but not `ioctl`; `io*` finds both), a term with punctuation such as `pve-node` or `key=val` is its words in a row with the last one as a prefix, and a quoted phrase is whole words in a row within one field. Each field is split once per row, so matching stays linear in the row's text; a regular expression passed by a caller decides on its own; while the operators are incomplete (for example `error OR` as it is typed), every word must match. Placeholder: `Search logs, e.g. "disk full", error OR timeout, app:nginx`. A `?` button inside the right edge of the search box (left of the clear button) opens a popover with one example each: words (all must match, as prefixes: `time` finds `timeout`), `io*` (a word of one or two letters matches only that word; `*` matches longer ones), `"exact phrase"`, `error OR timeout` and `auth NOT cron` (any case), `app:nginx`, `host:pve-node2` and `msg:"disk full"`. It closes on Esc, an outside click or when focus leaves it.
  * Filters apply as they change; the search icon button next to the box ("Search now", same as Enter) runs the search at once. In the mobile filter drawer, "Done" closes the drawer and runs the search. On phones (below the `md` breakpoint) the search box and the search button have a line of their own. The line below starts with the Filters drawer button, then the match count and Reset while filters are set (Filters and Reset as icons with their count badge), followed by the quick filters and the stream controls, so phones need no separate quick filters band. The search syntax help opens under the box, across its full width on phones.
  * Time selector with presets (Last 15m, 1h, 6h, 24h, 7d and Today, which starts at 00:00 in the server time zone) and a custom date and timestamp picker for bounded historical queries. Presets are saved as relative values, so a saved view keeps meaning "the last hour"; links and saved views carrying `since_midnight` show Today.
  * Multi-select dropdown facet filters for Host Alias (`source_alias`), Source IP, and Container/Application Name (`app_name`). The host and app lists hold at most 500 entries each; when a list was capped, the dropdown (and the mobile filter drawer) shows a note such as "Showing the first 500 hosts. Type a name to add others.", with the number taken from the facets response (`limit`).
  * Numerical severity threshold slider and filter pills (RFC 5424 numerical priorities 0 = Emergency through 7 = Debug).
  * Active filters are marked where they are set, in the toolbar and in the mobile filter drawer: the Host, App, Severity and Time controls get an accent border, accent value text and a clear button ("Clear host / ip filter", "Clear app / container filter", "Clear severity filter", "Clear time filter") that resets that control only, and the search box gets the accent border while it has a query. Time counts as active for any preset but All Time, or a From or To date. The Reset count is the number of active controls, each host and app counting once (`activeFilterControls` in `LogSearchBar.tsx` decides both). The Filters and Reset buttons are named by their text with the count ("Filters 3 active", "Reset 3 active filters"; on the phone toolbar the words are read but not shown), and the Host and App triggers by their label, value and count ("Host / IP: pve-node1 (+1) 2 selected"). In the toolbar and the drawer, as in the form variant, each clear button sits over its trigger as a sibling, never inside the `role="button"` element. Severity and Time (toolbar and drawer) are `SelectDropdown`, a single-choice list in the same box as Host and App (`dropdownStyles.ts`), not native selects: a `button` with `aria-haspopup="listbox"`, named by its label and value ("Severity: Error+ (0-3)"; in the drawer by the label above it), opening a `role="listbox"` that takes focus and marks the active row with `aria-activedescendant`. Enter, Space, Down, Up or Alt+Down open it on the chosen row; Up, Down, Home and End move, a typed letter jumps to the next row starting with it, Enter or Space chooses (a click or tap does too); Esc and Tab close it without choosing and focus returns to the trigger (Tab then moves on). The list opens upwards when there is no room below. Every other single-choice list in the app (the alert rule, preset, test, drop rule, maintenance schedule and AI analysis dialogs, and Settings) is a `SelectDropdown` too, in its `panel` variant: a full-width field named by the visible label above it (`labelledBy`, or a hidden label from its `label` prop where there is none, as for Add Fallback Model). Its list is fixed to the viewport, so a dialog's scrolling body never clips it, and stays beside the trigger in the DOM, inside the dialog and its Tab trap: it opens below the trigger, or above it when it does not fit below and there is more room above, at most 288 px tall and never past the viewport less 8 px, and scrolls within that; it follows the trigger when the page scrolls. Long rows (AI model names) wrap. A disabled one (the daily digest's channel while the digest is off) stays shut. No native `<select>` is left. Custom... shows From and To in the toolbar as two boxes of the dropdowns' height (26 px), so the row keeps its height.
* **Saved Views Menu:**
  * Quick-load saved search filters.
  * Persist current query parameters with custom display names.
  * Pin frequently accessed views directly to the filter bar.
  * A view is active when the current filters equal its saved filters (lists compared sorted; empty text, empty lists and missing values count as the same). The desktop button then reads `View: <name>` with an accent border, and `Views` otherwise; the active view is highlighted in the dropdown and in the mobile drawer.
  * Each view has Pin, Rename (pencil) and Delete actions, in the desktop dropdown and on the mobile drawer chips. Rename opens a "Rename Saved View" dialog with the name selected; Save is disabled while the name is empty or unchanged. The new name shows at once in the dropdown, the pinned chips and the button label.
  * Names are unique, ignoring case. The Save View and Rename dialogs warn "A saved view with this name already exists." while typing, and show the server's message if another tab took the name first. Changing only the case of a view's own name is allowed.
* **Log Detail & Context Inspector:**
  * Slide-over inspection drawer presenting parsed metadata, source IP, facility, formatted homelab timestamp (with a UTC offset badge such as `UTC+01:00`, worked out for each timestamp so logs from either side of a daylight saving change show the offset they had), secondary database UTC reference line, and raw unparsed syslog payload.
  * Order: a header with the severity badge, app, host and IP, and the actions (host action, Create Drop Rule, Create Alert Rule, Delete, Explain with AI); then on tablets and desktops the timestamp, received at, facility and severity code cards, the message, the raw record and the context. On phones (below `sm`) the message comes right after the actions, so it shows without scrolling and Newer and Older visibly change it: the message, the raw record, then the four cards, then the context. There the first four actions sit in two columns, with Explain with AI across both below them. Only the visual order changes (CSS `order`); the cards hold no controls, so the Tab order still follows the screen.
  * Protocol-aware host actions: A record is a Docker record when its raw text does not start with a syslog `<PRI>` and its `source_alias` is a configured Docker host alias ("Edit Docker Host") or a former one from `former_docker_aliases` in the facets response, or its `source_ip` is `docker` ("Configure Docker Host", which opens a notice in `/settings/sources` to re-add the host or add a syslog host alias for its address; the notice says the old container logs keep their Docker label). Other records (syslog and HTTP ingest) get quick-add and edit actions for host IP aliases. The live stream uses the same alias set, so a former Docker host's rows keep their alias instead of the syslog alias of their address; rows loaded before the Docker hosts and the facets response arrive get their stored alias (`storedSourceAlias`) back once the set is known (`restoreDockerAliases`).
  * One-click action to fetch surrounding context lines formatted in the configured homelab timezone (symmetric 10 entries around selected record). The lines are listed newest first, like the log stream. Each context line shows its severity badge and app name; the app name is left out when "Same App Only" is checked.
  * "Newer" and "Older" buttons step to the row above or below in the newest-first list; Up or K and Down or J do the same while the drawer is open, except in a text field or while another dialog is open on top.
  * "Explain with AI" and "Inspect Target + Context" open the AI analysis dialog on top of the drawer, which stays open on the same log: closing the dialog shows it again, and focus returns to the button that opened it (see Dialogs below).
  * "Create Drop Rule" prefills the host field with the host alias (the IP when the host has no alias).
  * "Create Alert Rule" (next to "Create Drop Rule") switches to Rules & History > Alert Rules and opens the new-rule dialog with the name `Alert on <app>`, the app filter set to the log's app when it is a known app, severity and pattern empty, and a read-only "From log: <message>" line under the pattern field (truncated, full text in the tooltip). The prefill is handed over in memory (`utils/alertRuleHandoff.ts`, read once by `AlertsPanel`), never in the URL. Closing the dialog stays on Alert Rules.
* **Targeted Log Deletion Modal:**
  * Supports deletion of selected records, filtered ranges, or all historical logs with confirmation guards and dry-run count preview.
  * The Custom Range From and To fields are read in the server's time zone (`TZ`), like the Console's date pickers, and their labels name that zone.

### 3.2 Rules & Alerts Hub (`/rules`)
* **Alert Rules Tab:**
  * Full CRUD management for threshold, pattern match, and spike alert rules.
  * Configure Apprise notification targets, sliding evaluation windows, cooldown suppression periods, and optional automated AI root-cause incident enrichment.
  * Dry-run pattern testing against historical logs and JSON bundle export/import.
* **Automated AI Redaction Notice:**
  * When rules with AI enrichment are enabled, the UI renders prominent notices explaining that triggering events are dispatched automatically to external AI providers without manual review, that automated scrubbing operates on a best-effort basis, and that automated triggers consume API tokens.
* **Drop Rules Tab:**
  * Pre-storage discard filters (keyword or regex) matching message content, application names, or sources, with severity thresholds.
  * The Create and Edit dialog picks hosts and apps with `MultiSelectDropdown` (`variant="form"`, typed patterns such as `router*` added as entries), as the alert rule dialog's app filter does; each trigger is named by its label and its selection. A saved list opens as one entry per pattern, and a list longer than 255 characters shows an error and keeps Save disabled. The Dry-Run sample host and app start from the first entry. The dialog loads the syslog host aliases (`GET /api/aliases`) when it opens: in the host list an alias shows its IP and an aliased IP shows "alias <name>" (`optionHint`; the search box matches it too), and each selected IP that has an alias gets a note under the field that the rule drops that host's logs either way. If the aliases cannot be loaded, no hints are shown. The list shows "Hosts:" and "Apps:" for rules with several. In the form variant, the clear button sits over the trigger as its sibling (not inside it), the count badge is part of the trigger's name ("3 selected"), and the open list is portaled into the enclosing dialog (else `document.body`), so it is inside the `aria-modal` dialog and its Tab trap.
  * Displays live dropped counters per rule, counter reset actions, dry-run testing against recent logs, and JSON export/import.
* **Alert History Tab:**
  * Unified incident history covering triggered alert rules, automated AI rule enrichments, and scheduled daily analytical digest dispatches.
  * Detail inspection drawer (rendered via `IncidentHistoryDetail.tsx`) presents full prompt envelopes, model badges, incident summaries, and token consumption breakdowns (input, output, reasoning/thought, and total).
  * `/rules/history?id=N` (the link in alert notifications) loads record `N` with `GET /api/alerts/history/{id}` and opens its detail, wherever it falls in the paged list. Closing it removes `id` from the URL. A record that no longer exists (deleted, or pruned by retention) shows an error message instead.
  * Rule alerts (not Daily Digest or On-Demand items) show an "Inspect in Console" button in the detail header and a smaller "View in Console" link next to "Triggering Log Snippet". Both open the Console with `source=<source_alias>` (when set), `time=<start>` and `to=<triggered_at + 1 minute>` as UTC ISO strings, plus `focus=<sample_log_id>` when the alert recorded its triggering log; the start is `triggered_at` minus the larger of 1 minute and the rule's `window_seconds` (1 minute when the rule is not loaded). The range is host-wide; "Same app only" adds `app=<app_name>` when the alert has an app.
  * Analyses with an AI audit record (on-demand analyses and alert enrichments) show an expandable **Follow-up Discussion** section below the diagnosis. Messages load on first expand, and the thread stays mounted when collapsed so a streaming reply is not lost.
  * Supports single-item and bulk history deletion.
* **Maintenance Window Tab:**
  * Configure active on-demand alert suppression periods or recurring schedules by day of week and time window to silence alerts during routine maintenance.
  * The presets (1, 4, 8 and 24 hours) and the specific end time each start a new session; their label reads "Set end time from now", or "Start a new window" while one is running. "Active Concurrent Sessions" lists every active session (web UI, API token or MCP) with "+1h" (aria-label "Extend session <reason> by one hour", which calls `POST /api/alerts/maintenance/sessions/{session_id}/extend`) and "Stop Session".
* **Alert and Drop Presets Dialogs:**
  * 1-click installation of the alert presets (20: security, disks and storage, backups, power, network, Proxmox, system) and drop presets (12: DNS, firewall, health checks, Proxmox, systemd, smartd, Radarr and Sonarr, Home Assistant) listed in `docs/RULES_GUIDE.md`. Installing a preset again adds another rule.
  * A **Category** field (`SelectDropdown` panel, `PresetCategoryFilter.tsx`) above the cards shows all categories or one, each with its count. Cards are sorted by category in a fixed order (Security, Storage and disks, Backups, Power, Network, VMs and containers, System, Apps, then any custom category, then Other for custom presets without one). The choice goes back to all categories when the dialog closes.

### 3.3 On-Demand AI Analysis Modal
* **Scrubbed Preview:** Redacted log preview displaying the exact scrubbed text to be dispatched (with one-click clipboard copy).
* **Token Estimator & Model Picker:** Live token counter and active model selection.
* **Situational Context:** Free-text user context textarea to provide situational background (e.g., recent system updates, topology changes).
* **Structured Markdown Display:** Formatted analysis presentation including Summary, Root Cause, and Remediation steps with copyable command and configuration blocks. `MarkdownRenderer` nests lists at most 10 deep; deeper list content is shown as plain text, so an answer with thousands of nested list markers cannot overflow the browser's call stack.
* **Follow-up Discussion (`AiFollowUpThread.tsx`):** Rendered below the Actionable Remediation card once a diagnosis completes (shared with Incident History). Shows the thread with Markdown replies (copyable code blocks), model and token badges per reply, a running token tally and an `X / 10 turns` counter. Replies stream in over SSE; partial text is discarded when a failover restarts the reply on a fallback model. The question box sends on Ctrl+Enter or Cmd+Enter and keeps 44px touch targets on mobile. The view follows new content unless the operator has scrolled up. After the 10th question an advisory replaces the input. "Clear Thread" asks for confirmation, then resets the conversation while keeping the diagnosis. Follow-ups in the modal reuse the provider, model and fallback order selected for the diagnosis.

### 3.4 Storage Management Panel (`/storage`)
* **Current Storage Card:** Dual-metric display showing active Database Footprint (MB/GB) alongside a visual progress bar for Available Mount Disk Space.
* **30-Day Storage Trend Chart:** Compact line and area chart (via `recharts`) plotting database disk footprint and total log volume over the past 30 days.
* **Maintenance Actions:** Manual trigger for log purge, FTS5 index compaction, WAL truncation, and SQLite vacuum with real-time UI updates.

### 3.5 Settings Panel (`/settings`)
* **Application Settings:** Encrypted API key management (Google Gemini, Anthropic Claude, OpenAI / custom OpenAI-compatible endpoint like Ollama/vLLM), dynamic model discovery with 24-hour cache, multi-model failover configuration, custom system prompt, retention slider (1 to 30 days, capped by `MAX_RETENTION_DAYS`), internal log level, and GHCR release update check toggle.
* **Notification Channels Card:** Configure Apprise push notification targets (Discord, Telegram, Slack, Pushover, email, webhook, etc.) with live test dispatch, and schedule daily analytical digests (`NotificationsCard.tsx`). The digest runs on the server clock (`TZ`), so its "Schedule Time" field names the server zone, for example "Schedule Time (Europe/London)", or "(server time)" when `server_timezone` is `null`.
* **API & MCP Access (`/settings/api-tokens`):** Scoped Bearer token lifecycle management (create from a preset or a custom scope list, copy raw secret once, rename, change scopes, and revoke) alongside Model Context Protocol (MCP) server administration (`ApiTokensTab.tsx`). Features master server activation toggle (off by default), live endpoint display (Remote SSE / Streamable HTTP), and three collapsible accordion client configuration guides with one-click copy blocks:
  1. Claude Desktop (Remote via `mcp-proxy`) for remote Proxmox, NAS, or external servers.
  2. Cursor / Windsurf / Antigravity (Remote SSE / Streamable HTTP) for direct network IDE integrations.
  3. Claude Desktop (Local Docker Stdio) for local single-machine Docker deployments.
* **Sources Management (`/settings/sources`):** Unified panel coordinating log source identities across protocols (`SourcesTab.tsx`). Combines two primary views:
  * **Docker Hosts (`DockerHostsTab.tsx`):** Dedicated management panel for multi-host Docker log collection. Features live status badges (Connected, Reconnecting, Disabled, Error), active container counts, latency metrics, ad-hoc connection test buttons, and an Add/Edit host modal supporting mutual TLS (CA cert, client cert, and encrypted client key).
  * **Host Aliases (`HostAliasManager.tsx`):** Dedicated table to manage IP-to-Hostname mappings for Syslog sources (e.g., `192.168.1.1` -> `OPNsense Firewall`) with quick-add prompts for newly detected, unmapped IP addresses.
  * **Backward Compatibility:** Accessing legacy `/settings/aliases` automatically redirects to `/settings/sources`.
* **Advanced Settings (`/settings/advanced`):** Runtime controls for AI timeout, reasoning token budget, base application URL, private IP webhook targets, Docker collector toggle and exclusions, trusted proxy headers, cookie security, and Syslog TCP connection ceilings (`AdvancedSettingsCard.tsx`).

## 4. Theme & Visual Styling
* **Dark Operations Aesthetic:** Native dark canvas (`color-scheme: dark;` background `#070a10`) tailored for server operations environments.
* **Accent Shades:** `accent` in `frontend/tailwind.config.js` is Tailwind's sky scale, shades 200 to 950 (`accent-500` is `#0ea5e9`). Light shades (200 to 400) are for text and icons on the dark canvas; dark shades (800 to 950, usually with opacity) for tinted backgrounds and borders. A shade missing from the config produces no CSS at all, so add it there before using it.
* **Typography:** Clean sans-serif typography (`Inter`, system-ui) paired with monospace fonts for logs, timestamps, IP addresses, and code snippets.
* **Layout Stability:** Built-in `scrollbar-gutter: stable` and slim scrollbars (`::-webkit-scrollbar`) to eliminate layout shifts when virtual lists update.
* **Accessibility Baseline:** Every page passes the axe rules run by the UI check at 375, 640, 767 and 1280 px. The viewport allows pinch zoom (no `maximum-scale`). Each page has one `<h1>` (visually hidden on the logged-in pages, named after the navbar entry) inside a `<main>` landmark, including login and first-run setup. White text sits on `bg-accent-700` (`#0369a1`, 5.9:1), with `hover:bg-accent-600`; `accent-600` behind white text gives only 4.1:1. Form controls have a label (`<label htmlFor>` for the alert rule dialog's fields, the label and value for every `SelectDropdown`, `aria-label` for the retention slider), a control's name contains its visible text, the Console log list has the keyboard row cursor above, and scrolling code examples (the maintenance cURL commands) are focusable regions. The UI check also covers Incident History, an open incident and Maintenance, and `.scripts/ui-check/keyboard.mjs` (maintainer tooling) checks the row cursor and dialog focus with the keyboard only.
* **Dialogs:** `Modal`, `SlideOver` and the API token dialogs are `role="dialog"` with `aria-modal="true"`, named by their title (an `h2`, `aria-labelledby`; headings inside a dialog start at `h3`). `useDialog` in `utils/dialogStack.ts` keeps one stack of open dialogs with one keydown listener: Esc closes only the top dialog, Tab and Shift+Tab wrap inside it, opening moves focus in (an `autoFocus` field keeps it, else the first `data-autofocus` element, else the dialog itself), and closing returns focus to the element that opened it, or, when that element has gone with a dialog this one replaced (Create Drop Rule replaces the log drawer), to that dialog's opener. Dropdowns and menus that handle Esc themselves (`MultiSelectDropdown`, `SelectDropdown`, `SavedViewsMenu`) take it in the capture phase and stop it, so they close before the dialog around them; while one of the Saved Views menu's own dialogs is open, that dialog takes Esc. The one-time API token dialog ignores Esc, because the token cannot be shown again. While any dialog is open, the page's `overscroll-behavior` is `none` (on `html` and `body`, restored when the last one closes), so a swipe on a backdrop or a short dialog cannot start a phone browser's own pull-to-refresh either.

## 5. Build & Asset Distribution
* **Vite Bundling:** Vite compiles production static assets directly into `backend/app/static/`. After the build, a plugin in `frontend/vite.config.ts` writes a Brotli (`.br`, quality 11) and a gzip (`.gz`, level 9) copy next to each `.js`, `.mjs`, `.css`, `.html`, `.svg` and `.json` file of at least 512 bytes, the copied `/docs-assets/` included, keeping each copy only when it is at least 10% smaller. It uses Node.js's built-in `zlib`.
* **FastAPI Static Serving:** `backend/app/core/static_files.py` serves the build: `/assets/` from a `StaticFiles` mount, other files by path, and `index.html` for every other path (SPA fallback; `/api` and `/mcp` paths return `404`). When a `.br` or `.gz` copy exists and the request's `Accept-Encoding` allows it (q above 0; Brotli first), that copy is sent with `Content-Encoding` and the original file's content type, and every response for such a file carries `Vary: Accept-Encoding`. Each copy has its own `ETag`, and `If-None-Match` or `If-Modified-Since` get `304`. Content-hashed files under `/assets/` are sent with `Cache-Control: public, max-age=31536000, immutable`; `index.html` and every other unhashed file with `no-cache`, so a new release loads at once. Nothing is compressed at request time, so API responses and the SSE streams are never compressed or buffered.
